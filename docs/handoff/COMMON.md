# 스펙 handoff 공통 규칙 (모든 스펙에 적용)

> 이 문서는 TrendsIT의 모든 구현 스펙(S0, S1, ...)에 공통으로 적용된다. 각 스펙의 `S<n>_TASK.md`가 이 문서보다 우선한다.
> 작성: 2026-10-07. 같은 날 갱신: 6.1 역할 md 작성 규칙, 관문 B 통과 기준을 예/아니오 질문으로, judge 맞추기(문서 35 프롬프트 작성 가이드 반영). 2026-10-08 갱신: 8장 일정 열 삭제(일정은 저장소에 두지 않음), 9장 병행 개발, 10장 검증 산출물, 11장 맥 확인 단계. 맥락 전체는 `docs/CONTEXT.md`.

## 1. 일하는 방식

```
설계 세션(Claude, 기획 담당)  ── handoff(스펙 문서) ──▶  코드 세션(Claude Code, 구현 담당)
                                                          │ 탐색 → 계획 → 구현 → 관문 A → 관문 B → 자체 리뷰
설계 세션이 GitHub에서 리뷰  ◀── PR + 리포트 ─────────────┘
```

- 코드 세션은 스펙을 끝까지 읽고, 모호한 점이 구현 방향을 바꿀 정도면 **추측하지 말고 멈춰서 질문을 PR 설명이나 `reports/S<n>_questions.md`에 남긴다.** 사소한 것은 합리적으로 정하고 리포트에 "결정한 것"으로 적는다
- 스펙 범위 밖 기능을 미리 만들지 않는다. 필요해 보이면 리포트의 "다음 스펙 제안"에 적는다
- 저장소: GitHub 비공개 `trendsit`. 스펙마다 브랜치 `s<n>-<짧은이름>` → PR → 설계 세션 리뷰 → 사용자 병합
- 커밋 메시지: `<종류>(s<n>): <무엇을>` 한 줄, 종류는 feat / fix / docs / test / refactor / chore. 예: `feat(s1): GeekNews 목록 페이지 백필`. 여러 단계 스펙은 단계 이름을 본문 첫 줄에(`1a S0 보완`)
- PR 설명은 `.github/pull_request_template.md` 양식(7장 항목). CI(ruff + pytest, 네트워크·비밀 없이)가 초록이어야 리뷰
- 문서 역할: **README = 현재 상태 설명서**(스펙이 끝날 때마다 기능, 빠른 시작, 성과 수치, 로드맵 갱신), **위키 = 과정 기록**(설계 세션이 관리. 코드 세션은 위키를 쓰지 않음). 오래 남길 설계 문서는 `docs/`(ADR은 `docs/adr/`)

## 2. 두 관문

### 관문 A: 구현 완료 (PASS/FAIL)
- 스펙마다 `scripts/verify_s<n>.sh`를 만든다. 항목마다 `PASS`/`FAIL`과 이유를 한 줄씩 출력하고, 하나라도 FAIL이면 종료 코드 1
- 항목은 각 스펙의 "관문 A" 표 그대로. 항목을 빼거나 기준을 낮추지 않는다
- 이전 스펙의 verify 스크립트도 계속 통과해야 한다(회귀)

### 관문 B: 결과 완성도 (점수 + 문턱값)
- LLM 결과물이 있는 스펙에만. 각 스펙의 "관문 B" 표에 채점 항목, 채점표, 문턱값이 있다
- 채점 순서: **코드 채점 → LLM 채점 → 사람 확인**
  - 코드 채점: 셀 수 있는 것(스키마, 근거 id 존재, 수치 문자열 일치, 금지 표현, 개수)
  - LLM 채점: 의미 판단(충실성, 정확성, 핵심 포착). 채점자는 `models.yaml`의 `judge`(gemini-3.8-flash)
    - **통과 기준은 항목별 예/아니오 질문 + 한 줄 비평.** 채점표의 질문 문장을 그대로 프롬프트에 넣는다. 출력 칸 순서는 비평 → 판정(pass/fail). 1~5점은 같은 호출에서 함께 받아 보고용으로만 기록
    - 채점 프롬프트에 "길이나 자신감이 아니라 근거와의 일치로 판단한다"를 넣는다(길이 편향). 후보를 비교할 때는 순서를 바꿔 두 번(위치 편향)
    - 같은 계열 모델끼리 채점하지 않는다(현재 generate = Qwen, judge = Gemini)
  - 코드 채점을 통과한 항목만 LLM 채점으로 보낸다(비용 절약)
- **judge 맞추기(사람 라벨):** judge 점수에 기대는 관문 B는 사람 라벨로 judge를 먼저 확인한다
  - 코드가 라벨 파일 `eval/labels/<역할>.csv`(id, 입력 요약, 출력, pass 빈칸, critique 빈칸)를 만들고 사용자가 채운다. 역할당 20건(S0의 repo_oneliner는 10건)
  - `eval <역할> --agreement`: 항목별 judge·사람 일치율. **80% 미만이면 사람 비평을 judge 프롬프트 예시로 넣고 다시 잰다(최대 3회, 관문 B 반복과 별도).** 그래도 미달이면 그 항목은 사람 판정을 기준으로 하고 리포트에 적는다
  - 라벨이 아직 없으면 judge 결과는 "잠정"으로 표시하고 PR을 낸다. 라벨은 설계 세션 리뷰 때 사용자가 단다
- 결과는 `reports/S<n>_quality.md`: 항목별 통과율 표(+ 보고용 평균 점수), 문턱값 통과 여부, **가장 나쁜 사례 3개(입력, 출력, 채점 비평)**, 반복 기록(프롬프트 해시, 바꾼 것 한 가지, 전후 통과율), judge 일치율(라벨이 있으면)

## 3. 자체 루프 규칙
1. 관문 A가 전부 PASS가 될 때까지 고친다
2. 관문 B를 돌린다. 문턱값 미달이면 실패 사례 출력을 직접 읽고(점수보다 출력이 먼저) 원인을 분류한다: 지시를 어김 / 기준이 모호함 / 예시를 베낌 / 입력에 정보가 없음 / 모델 한계
   - **한 번에 하나만 바꾼다.** 순서: md 문구 → 예시 교체 → 스키마 칸 순서 → 코드 규칙 → 모델. 입력에 정보가 없으면 프롬프트가 아니라 입력 조립 코드를 고친다
   - 같은 픽스처로 다시 돌려 전후를 비교한다(프롬프트 해시로 구분)
   - 실제 실행에서 나온 실패는 `role --replay`로 재현해 픽스처로 **추가**할 수 있다(기존 픽스처 수정·삭제는 금지, 추가한 것은 리포트에 표시)
3. **관문 B 반복은 최대 3회.** 3회 후에도 미달이면 멈추고, 리포트에 막힌 이유와 시도한 것을 남긴다(실패를 숨기지 않는다)
4. 마지막에 **새 컨텍스트의 서브에이전트**에게 "스펙 문서 + diff + 리포트"만 주고 대조 리뷰를 받는다. 지적 사항을 반영하거나, 반영하지 않은 이유를 리포트에 적는다
5. 커밋, 푸시, PR

### 하지 않는 것 (통과를 위한 지름길 금지)
- 픽스처, 채점기, 채점표, 문턱값을 바꿔서 통과시키기
- 기대 출력을 코드나 프롬프트에 그대로 박아 넣기, 특정 픽스처만 맞추는 분기
- 테스트를 약하게 만들거나 건너뛰기(`skip`, 넓은 `except`)
- 예산을 넘기는 실행. 상한에 걸리면 멈추고 보고

## 4. API 예산 (최소 구현 단계 전체 20달러, 2026-10-07 2달러에서 수정)
- OpenRouter 크레딧은 남은 수업에도 써야 한다. **최소 구현 단계(S0~S6) 전체 사용액 20달러 이내**
- 배분: 생성 11 / 채점 4 / 비교, 상한선 측정 2 / 예비 3. 스펙별 상한은 각 TASK 문서와 `config/budget.yaml`
- OpenRouter 키에는 다른 용도와 함께 쓰는 **공통 한도 50달러**가 이미 걸려 있어 바꾸지 않는다. 20달러 상한은 **코드가 지킨다**. 여유가 생겼어도 캐시, 작은 샘플, 무료 모델(배관 확인) 원칙은 그대로
- 장치(S0에서 만들고 이후 계속 사용)
  - 모든 요청에 `usage: {"include": true}`를 넣어 응답의 `usage.cost`(실제 청구액)를 받고, 호출마다 실행 기록에 저장
  - 단계 시작 시 `GET /api/v1/key`의 `usage`(누적 사용액)를 기준값으로 저장. **단계 사용액 = 현재 키 usage − 기준값.** 실행 시작마다, 그리고 큰 실행 전에 다시 조회해 확인(다른 곳에서 쓴 사용량까지 반영됨). `limit_remaining`도 함께 기록
  - 호출 전 예상 비용(입력 토큰 + max_tokens × 단가)으로 스펙 상한, 단계 상한 초과를 막음. 넘으면 예외로 멈춤
  - 응답 캐시: 같은 모델, 제공사, 메시지, 설정, 스키마면 저장된 응답 재사용(0원)
  - 개발 중에는 작은 샘플(1일치, 5건)로. 큰 실행은 스펙 끝에 1회
  - 생성은 추론 모드 끔 + 역할별 max_tokens. 채점은 가능한 싼 요금 등급 + 추론 토큰 상한
  - 배관 확인처럼 품질이 상관없는 실행은 무료 모델(`models.yaml`의 `smoke`)
- 리포트에 스펙별 사용액(모델별)을 표로 남긴다: `trendsit cost --spec S<n>`

## 6. 설계 원칙 (코드 리뷰 때 보는 것)
- **흐름은 코드, LLM은 판단 지점만, 에이전트(도구 루프)는 단계 수를 미리 모르는 곳만**
- **모델이 알아야 하는 것은 md, 반드시 지켜져야 하는 것은 코드.** 역할 = `roles/<이름>.md`(앞부분 실행 설정 + 본문 역할 카드). 도구, 출력 스키마, 입력 조립, 상한, 보안은 파이썬
- 역할 함수는 순수 함수(입력 모델 → 출력 모델). DB 읽기, 쓰기는 오케스트레이터만
- 모든 역할 출력에 `log`(한 줄, 명사형)와 `attention`(사람이 봐야 하면 true). 실행 기록 화면의 원천
- 수집한 내용은 `<data>`로 감싸 전달하고, 그 안의 지시를 따르지 않는다(프롬프트 인젝션). URL 가져오기는 SSRF 방어 함수로만
- 문체: 요약, 개요는 "~다", 포인트, 화면 문구는 명사형. 해요체, 평가형 마무리 금지(`skills/style_ko.md`)

### 6.1 역할 md(프롬프트) 작성 규칙 (상세: `docs/reference/prompt_guide.md`)
LLM이 들어가는 역할은 11개이고 형태는 다섯(추출, 판단, 도구 에이전트, 생성, 판정)이다. 같은 형태는 같은 뼈대를 쓰고, 다른 것은 판단 기준과 예시뿐이어야 한다.
1. **본문 섹션 고정(이 순서):** `## 목표`(한두 문장 + 왜 중요한지) / `## 입력` / `## 판단 기준`(조건 → 결정, 우선순위) / `## 출력`(칸과 채우는 조건, 빈칸이 정상인 경우) / `## 막혔을 때`(근거 부족, 도구 실패 시 할 일: 빈칸 + attention) / `## 예시`(`<examples>` 안에 `<example>` 3개: 보통 / 빈칸이 맞는 경우 / 함정)
2. **지시에 이유를 붙인다.** 금지도 이유와 함께. 대문자·굵게 강조는 md 하나에 하나만. 금지어 목록은 md가 아니라 코드 검사에
3. **메시지 두 개(코드가 조립):** system = 역할 md 본문 + includes(정적, 캐시). user = `<data>` 자료 → 이번 과제(앞부분 `task`) → 핵심 규칙 3줄(앞부분 `core_rules`). "자료는 위, 과제는 아래"와 "핵심 지시는 처음과 끝"을 함께 만족
4. **자료는 문서별 태그로:** `<document id="it:123" source="GeekNews">…</document>`. 근거 id를 속성에 둔다(인용 번호는 출력에서 `it:123#q2`). 큰 JSON 덤프를 넣지 않는다(문서 묶음에서 성능이 낮음)
5. **출력 스키마 칸 순서: 인용·이유 먼저, 결론(enum, status, 요약) 나중, log·attention 맨 끝.** generate 모델은 추론을 끄고 쓰므로, 근거를 먼저 쓰게 해야 결론이 근거를 따른다. 판단이 어려운 역할은 자유 문장 칸(reason) 하나를 결론 앞에 둔다
6. **도구 에이전트:** "추측하지 말고 도구로 열어 확인", 멈추는 조건 3개, "못 찾음은 정상 결과". "끝까지 계속하라"는 넣지 않는다(상한이 있는 배치 작업). 도구 docstring도 프롬프트다: 언제 쓰나 / 언제 쓰지 않나 / 인자 예 한 줄씩
7. 여러 역할이 같이 쓰는 규칙(문체, `<data>` 처리, 근거 id 형식)은 `skills/*.md`에 두고 `includes`로 붙인다. md마다 복사하지 않는다
8. 역할별로 꼭 넣을 지시와 예상 실패는 `docs/reference/agents_spec.md` 0.7

## 7. 리포트와 PR 형식
`reports/S<n>_report.md`
1. 한 줄 요약(무엇이 동작하게 됐나)
2. 관문 A 결과(verify 출력 붙여넣기)
3. 관문 B 결과(있으면, `S<n>_quality.md` 요약)
4. 결정한 것(스펙에 없어서 정한 것과 이유)
5. 스펙과 다르게 한 것과 이유
6. 남은 문제, 다음 스펙 제안
7. 사용액 표(`trendsit cost --spec S<n>`)
7-1. README 갱신 내역(기능, 성과 수치, 로드맵 체크) + 위키에 올릴 만한 것(막혔다 푼 문제와 수치, 바꾼 결정) 메모 몇 줄. 설계 세션이 위키로 옮긴다
8. 서브에이전트 리뷰 지적과 처리

PR 설명은 1, 2, 3, 6, 7을 짧게. 리포트 파일 링크.

## 8. 스펙 순서 (2026-10-07 확정: 7개, MVP에 원본 추적, 레포 분석가 포함)
| 스펙 | 내용 | 스펙 안 단계 |
|---|---|---|
| S0 | 바탕: 레포 골격, 설정, LLM 호출(제공사 고정, 비용, 캐시, 예산), run_role / run_agent, 실행 기록, 재생, 평가 틀, 더미 역할 | - |
| S1 | 수집: 글 6(RSS + 백필), 유튜브(RSS + 메타데이터), GitHub(트렌딩 주간 페이지 + 추적 레포 릴리스), safe_fetch, 링크 판별, 키워드 매칭 | - |
| S2 | 글 1차 요약(원본 확인 필요 판정 포함) + 임베딩 필터 | - |
| S3 | 깊게 보기: 편집장 계획 + 글 분석가(원본 추적) + 레포 분석가 | 3a 편집장 계획 / 3b 글 분석가 / 3c 레포 분석가 |
| S4 | 영상 분석가(맥, youtube-analyze 방식 참고 직접 구현) | - |
| S5 | 주간 브리핑: 묶기, 과거 대조 + 편집장 선별 + 작성자 ⇄ 검수자(작성자 지침 v2, 도식 판단 라벨 세트) | 5a 묶기 / 5b 선별 / 5c 작성 ⇄ 검수 |
| S6 | 공개와 자동화: export(예시 JSON 형식) + 정적 사이트 연결 + 도식 렌더 검사 + nightly / weekly + launchd | 6a export, 사이트 / 6b 자동 실행 |

### 여러 단계가 있는 스펙의 규칙
- 단계마다 관문 A 항목, 커밋, 리포트의 진행 체크리스트를 따로 둔다. 맥락이 끊기면 `reports/S<n>_report.md`의 체크리스트를 보고 이어 간다
- 관문 B(품질)는 역할마다 따로 돌리고, 3회 개선 상한도 역할마다 적용한다. 한 역할이 막혀도 나머지 단계는 끝낸다
- 예산도 단계별로 나눠 둔다(TASK 문서에 명시)

### 범위를 줄여야 할 때
기능을 빼지 않고 깊이를 줄인다: 자동 실행은 시연 때 수동 실행으로 → 글 분석가 최대 깊이 2 고정 → 레포 분석가는 "코드 수집 + LLM 1회" 판정판. 순서와 범위는 리뷰 결과에 따라 바뀔 수 있다.

## 9. 병행 개발 (S2~S3와 S4를 동시에, 2026-10-08)
코드 세션 두 개가 서로 다른 브랜치에서 동시에 일한다. 묶음 A = S2~S3(클라우드 구현 → 맥 확인), 묶음 B = S4(맥). 겹치는 파일은 아래 규칙으로 나눈다.

| 겹치는 곳 | 규칙 |
|---|---|
| DB 마이그레이션 | 번호 키 등록 방식(`core/migrations.py`, S2 0단계). 번호 대역: S2~S3 = 10~19, S4 = 20~29, 이후 스펙은 설계 세션이 정함. 같은 테이블을 둘이 고치지 않는다(S4는 `video_*` 테이블만) |
| 출력·입력 스키마 | 스펙별 파일(`core/artifacts_text.py`, `core/artifacts_repo.py`, `core/artifacts_video.py`). `core/artifacts.py`는 공통 부모와 등록(INPUTS, OUTPUTS)만 |
| `config/budget.yaml`, `config/models.yaml`, `config/keywords.yaml` | 설계 세션 소유. 코드 세션은 고치지 않는다. 필요하면 질문 파일에. 스펙이 새로 만드는 설정 파일(`config/filter.yaml`, `config/deep.yaml`, `config/video.yaml`)은 그 스펙 소유 |
| 공통 코어(`core/role.py`, `agent.py`, `llm.py`, `render.py`, `budget.py`, `db.py`, `cache.py`, `trace.py`, `eval/graders.py`, `eval/run_eval.py`. 수정의 주인은 `CONTRACTS.md` 4장) | 원칙적으로 수정 금지. 꼭 필요하면 작은 별도 커밋으로 나누고 PR 설명 맨 위에 "공통 코어 수정"으로 표시 |
| `pyproject.toml`, `uv.lock` | 의존성은 선택 묶음으로 추가(S2~S3 `embed`, S4 `video`). 병합 때 `uv lock`을 다시 만들어 충돌 해결 |
| `trendsit/cli.py` | 새 명령은 스펙별 파일(`trendsit/cli_text.py`, `cli_video.py`)의 `register(sub)` 함수로 만들고 `cli.py`에는 등록 한 줄만 |
| README, `docs/DEVELOPMENT.md` | 자기 기능 행만 추가. 성과 표는 행 단위 |
| 교차 계약 | `docs/handoff/CONTRACTS.md`(영상 처리 지시 형식, 근거 id, 테이블 소유). 바꿔야 하면 질문 파일에 |

- 병합 순서: 먼저 끝난 쪽부터. 두 번째 PR은 main을 받아(`git merge origin/main`) 충돌을 해결하고, 병합된 트리에 있는 `scripts/verify_s*.sh` 전부와 pytest를 다시 돌린 결과를 PR 코멘트로 남긴 뒤 리뷰받는다
- 묶음 B는 `s2-0-base`가 병합되기 전에는 새 파일만 만든다. `core/artifacts.py`, `cli.py`, `pyproject.toml`, `core/db.py`·`migrations.py`는 그 PR을 받은 뒤에 손댄다
- 맥에서 두 세션이 동시에 돌면 같은 폴더를 쓰지 않는다. 브랜치마다 작업 폴더를 나눈다: `git worktree add ../trendsit-s2s3 s2-s3`(클라우드가 만든 브랜치를 받을 때), `git worktree add -b s4-video ../trendsit-s4`(새 브랜치). 폴더마다 `data/`는 따로(마이그레이션이 섞이지 않게)

## 10. 검증 산출물 (리뷰어가 직접 돌릴 수 없는 모델 출력)
리뷰 세션에는 API 키, 맥(Whisper, ffmpeg, MPS), 큰 모델이 없을 수 있다. 모델이 판단하는 단계마다 **파일만 보고 판단할 수 있는 산출물**을 `reports/` 아래에 남긴다(git 포함).
- 공통: 실행 환경과 모델(모델 id, 장치 CPU/MPS, 라이브러리 버전, 처리 건수, 걸린 시간)
- 역할 출력: 입력 요약과 출력을 나란히(관문 B 픽스처 전부), 코드 채점 실패 이유, judge 비평
- 임계값을 정하는 단계(임베딩 등): 점수 분포 표, 임계값과 그 근거, 판정 목록 CSV, 임계값 근처 사례
- 도구 에이전트: 항목별 도구 호출 경로(도구, 인자, 깊이, 결과 요약, 멈춘 이유)
- 이미지 판독: 저해상도 썸네일(영상당 최대 5장)과 판독 결과
- 재현 명령을 함께 적는다. 크기는 스펙당 수 MB 이내. 원본 영상·오디오·임베딩 벡터는 커밋하지 않는다
- 사람 확인이 필요한 곳은 체크 칸이 있는 표로(사용자가 리뷰 때 표시)

## 11. 맥 확인 단계 (클라우드에서 구현한 스펙)
운영은 맥(M1 Max 32GB)이다. 클라우드 세션이 구현한 스펙은 맥에서 한 번 확인한 뒤 리뷰한다.
1. 클라우드 세션: 구현, 관문 A·B, PR 생성. `reports/S<n>_mac_todo.md`(여러 스펙 묶음이면 `S2S3_mac_todo.md`처럼 묶음 이름)에 맥에서 확인할 것을 체크 칸 표로 남긴다(항목 / 클라우드에서 못 한 이유 / 확인 명령 / 기대 결과 / 결과 빈칸). PR 설명 맨 위에 "맥 확인 대기"라고 쓰고 그 뒤로는 푸시하지 않는다
2. 맥 세션: 그 브랜치를 worktree로 받아 `uv sync` → 목록대로 확인 → 결과를 같은 파일에 채우고, 고칠 것은 같은 브랜치에 커밋. 끝나면 PR 설명의 표시를 "맥 확인 완료"로 바꾼다
3. 리뷰는 "맥 확인 완료" 뒤에 시작한다
- 스펙 상한은 TASK 문서에 클라우드 몫과 맥 몫을 나눠 적는다. 실행 기록 DB가 따로라 맥 세션은 시작할 때 PR 리포트의 클라우드 사용액을 더해 확인한다. 단계 상한(20달러)은 키 기준이라 공통

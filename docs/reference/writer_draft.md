## 0. 원칙
- **형식은 정보의 모양이 정한다. 기본값은 문장이고, 도식은 문장으로 읽는 것보다 그림으로 보는 게 빠를 때만 쓴다**
- 두 방향을 같은 무게로 본다. 도식이 필요한 곳에서 빠뜨리는 것(누락)과 필요 없는 곳에 넣는 것(남발)은 같은 크기의 실수
- 작성자는 그리지 않는다. 수치와 사건을 구조화해서 내놓고, 그릴지는 코드 규칙이 정한다. 도식 종류는 **A~D 닫힌 목록**(소스 연결도, 수치 막대, 영상 타임라인, 사건 흐름)이고 그 밖의 도식(원그래프, 다축, 색·크기·위치에 모두 의미를 싣는 도식)은 만들지 않는다
- 결론 먼저(역피라미드). summary 첫 문장과 첫 point만 읽어도 요점을 얻게
- 필수 칸은 최소, 나머지는 근거가 조건을 넘을 때만. 빈 배열이 정상
- 분량은 근거 양에 비례. 모든 문장은 근거 id로 원문에 닿는다
- **모델에게는 "이렇게 쓴다"로 지시하고, 금지어 목록은 코드 정규식에만 둔다**(Anthropic 권고: 하지 말 것보다 할 것을 말하기, 형식 억제 문구는 모델에 따라 과하게 작동할 수 있음)

```markdown
# 작성자

## 목표
토픽 하나를 1~1.5화면 분량의 토픽 페이지로 쓴다. 읽는 사람이 3분 안에
"무슨 일이 있었고, 왜 중요하고, 원문 중 무엇을 열어 볼지" 알게 한다.

## 입력
- plan: 이 토픽의 순위, 다룰 축(angle) 한 줄, 후속 토픽이면 지난 토픽
- evidence: 이 토픽에 묶인 근거만. 각 근거에 id가 있다
  - 글: 요약, 핵심 주장, 수치, 원문 문장(quotes) — id `it:<번호>#q<n>`
  - 영상: 슬라이드 전용 수치, 타임라인 — id `vd:<번호>@<초>`
  - 레포: 하는 일 한 문장, 신호, 릴리스 — id `rp:<owner/name>`
- previous: 후속 토픽이면 지난 토픽의 요약과 포인트
- 수정 모드면: 이전 초안 + 검수 이슈 목록

## 출력 칸

| 칸 | 필수 | 쓰는 방식 | 분량 |
|---|---|---|---|
| title | 필수 | 무엇이 일어났는지 명사구. 쉼표로 두 부분까지 | 30자 안팎 |
| summary | 필수 | **첫 문장은 결론: 누가, 무엇을, 얼마나.** 둘째 문장에 쟁점이나 배경. "~다" | 1~2문장, 최대 3 |
| overview | 필수 | 무슨 일, 왜 중요한지, 쟁점 순서. "~다" | 2~4문장 |
| points | 필수 | 항목마다 새 정보 하나 + 근거 id. 완결된 1~2문장, 명사형 끝 | 소스 1개면 2~3개, 여러 개면 3~6개 |
| numbers | 선택 | 아래 "수치를 그룹으로 낼 때"에 해당할 때 | 그룹당 2~6개 |
| events | 선택 | 아래 "사건을 낼 때"에 해당할 때 | 2~6개 |
| concepts | 선택 | 기술 뉴스를 매주 읽는 개발자도 처음 볼 용어만 | 0~3개 |
| contributions | 선택 | 근거가 2개 이상 소스에서 왔을 때. 소스마다 그 소스에서만 나온 것 | 소스마다 1문장 |

선택 칸은 해당할 때만 채우고, 해당하지 않으면 빈 배열로 둔다.

## 정보의 모양에 맞는 자리

| 근거에 있는 정보 | 자리 |
|---|---|
| 같은 단위 값 3개 이상 비교 (모델별 점수, 회사별 가격) | numbers |
| 같은 단위 전후 비교, 그 차이가 summary의 결론 (도입 전 1.6초 → 후 150ms) | numbers (baseline 표시) |
| 같은 단위 값 2개 일반 비교 (A 86.6%, B 93.5%) | points 문장 한 줄 |
| 날짜가 다른 사건 3개 이상 | events |
| 날짜가 다른 사건 2개, 그 흐름 자체가 쟁점 | events + flow_is_point: true |
| 하나의 수치나 사실 | points 문장 안 |
| 처음 보는 용어 | concepts |
| 소스마다 다른 기여 | contributions |
| 방법, 구조, 절차 | points에 순서대로 |

판단이 애매하면 질문 하나로 정한다. **"이 비교나 흐름을 문장으로 읽는 것보다 그림으로 보는 게 빠른가?"**
빠르면 그 칸을 채우고, 비슷하면 문장으로 쓴다.

## 수치를 그룹으로 낼 때 (numbers)
- 같은 대상을 같은 단위로 비교하는 값이 3개 이상이거나, 전후 비교이고 그 차이가 summary에 나올 때
- 각 값은 근거 문장에 그대로 있는 숫자이고, 근거 id를 단다
- 비교는 이 토픽의 쟁점과 이어진다(overview나 points에서 언급)
- 형식: `{group, title, unit, items: [{label, value, ref, baseline?, emphasis?}], display?}`
  - title에는 발견을 쓴다. "모델별 성능" 대신 "Jeeves가 정확도 7%p 높음"
  - 한 그룹은 한 단위. 단위가 다르면 그룹을 나눈다
  - 강조할 값 하나에만 emphasis: true, 전후 비교의 이전 값에 baseline: true
- 슬라이드에서만 나온 수치는 해당 point 문장에 "발표 슬라이드 기준"이라고 쓴다

## 사건을 낼 때 (events)
- 날짜가 서로 다른 사건이 3개 이상일 때. 2개면 그 흐름이 쟁점일 때만 내고 flow_is_point: true
- 날짜는 근거에 있는 날짜만, YYYY-MM-DD. 같은 날 사건은 하나로 합친다
- 지난 토픽의 사건은 topic_id로 잇는다(후속 토픽)

## 영상 근거를 쓸 때
- 슬라이드 전용 수치나 핵심 장면을 쓰면 그 point의 ref에 `vd:<번호>@<초>`를 단다. 그 시각이 영상 타임라인에 표시된다

## points 쓰는 방식
- 첫 항목은 가장 중요한 사실, 마지막 항목은 남은 쟁점이나 확인할 점
- 수치는 숫자와 비교 대상을 함께: "응답 150ms, 기존 1.6초 대비 약 10배 빠름"
- 각 항목은 앞 항목에 없던 정보를 더한다
- 한 항목 1~2문장, 80자 안팎

## 문장을 쓰는 방식
- 근거에 있는 사실, 숫자, 날짜만 쓰고 문장마다 근거 id를 단다
- summary와 overview는 구체적인 주어로 시작한다(회사, 제품, 사람)
- 문장은 사실이나 쟁점으로 끝낸다. 평가는 근거가 직접 말한 경우에만 인용으로
- 원문은 요약해서 옮기고, 그대로 옮기는 것은 짧은 인용 한 구절까지
- 문체는 skills/style_ko.md를 따른다(요약, 개요는 "~다", 포인트는 명사형)

## 형광(==)
- summary 1개, overview 1개, points 항목당 최대 1개, 페이지 전체 3~4개
- 그 토픽의 핵심 결론이나 키워드에 쓴다. 제목, 개념, 출처, 수치 라벨에는 쓰지 않는다

## 후속 토픽
- overview 첫 문장에서 지난 흐름과 이번 변화를 잇고, 바뀐 것만 쓴다

## 수정 모드 → 별도 md `roles/writer_revise.md`로 분리
- md 맨 위: "이슈가 지적한 칸만 고친다. 나머지 문장은 그대로 둔다"(이유: 다른 문장까지 바꾸면 검수자가 이미 통과시킨 문장을 다시 봐야 한다)
- 고친 항목 번호를 changed에. 근거로 고칠 수 없는 이슈는 그 문장을 지운다
- 코드: 지적되지 않은 칸이 바뀌면 이전 라운드 값으로 되돌리고 log에 기록
- writer.md와 같은 includes(문체, 도식 규칙)를 쓰고, 입력은 이전 TopicPage + 이슈 목록 + 지적된 칸의 근거 원문만

## log
한 줄, 명사형. 예: "포인트 5개, 수치 그룹 1개, 사건 6개, 근거 id 9개"

## 예

summary:
"OpenAI가 Luna 기반 Decision API를, PostHog가 Jeeves를 같은 주에 공개했다.
쟁점은 ==정확도를 얻는 대신 지연이 늘어나는 맞교환==이다."
(첫 문장 = 누가, 무엇을. 둘째 문장 = 쟁점)

point:
"Decision API 응답 150ms, 기존 GPT-6 Luna 1.6초 대비 약 10배 빠름 [it:12#q2]"

값 2개 일반 비교 → 문장:
근거 "JevBench 정확도 Jev 86.6%, Jeeves 93.5%" →
point "JevBench 정확도 Jeeves 93.5%, Jev 86.6%보다 6.9%p 높음 [it:13#q1]". numbers는 비운다.

값 3개 이상 → numbers:
근거에 모델 4개의 JevBench 정확도가 있고 overview의 쟁점이 정확도 →
{group: "jevbench", title: "Jeeves가 4개 모델 중 정확도 최고", unit: "%", items: [... 4개, Jeeves emphasis]}

단위가 다른 두 수치 → 문장:
근거에 "정확도 93.5%"와 "응답 150ms"만 있음 → 각각 points 문장 안에.
```

## ② 코드 규칙

### 도식 선택 (export/diagrams.py)
도식 종류는 A~D만. 페이지당 최대 4개(연결도 포함).

| 도식 | 그리는 조건 | 안 그리는 경우 |
|---|---|---|
| A 소스 연결도 | 항상 | - |
| B 수치 막대 | numbers 그룹이 있고, 단위 하나, 모든 ref가 실제 근거이고, **items 3개 이상 또는 (items 2개 + baseline 표시 + summary에 그 그룹의 값이나 라벨이 나옴)** | 그룹이 2개 이상이면 overview에 언급된 그룹 하나만(나머지는 문장으로) |
| C 영상 타임라인 | 토픽에 영상 근거가 있고, points나 numbers가 인용한 영상 시각이 1개 이상 | 인용된 시각이 없으면 생략 |
| D 사건 흐름 | **events 3개 이상, 또는 2개 + flow_is_point**, 날짜 서로 다름 | 모든 사건이 같은 날 |
- 막대 제목은 작성자의 group title(발견)을 쓴다

### 출력 검사 (checks/writer.py, 검수자 앞)
- 필수 칸, 분량 상한(summary 3문장, overview 4문장, points 개수, 항목 최소 길이: 2~3단어짜리 항목 금지)
- 모든 point, number item, event에 ref, ref가 evidence에 실제로 있음
- numbers의 value 문자열이 ref 근거 문장(또는 OCR 텍스트)에 있음, 그룹 안 단위 하나, title 존재
- events 날짜 형식과 근거 존재
- concepts 3개 이하, contributions는 소스 2개 이상일 때만
- 형광 개수와 위치
- **금지어 정규식(모델 지침에는 넣지 않음):** 해요체(`요\.`, `요$`), 평가형 마무리("눈에 띈다", "핵심이다", "주목할 만하다", "공통 교훈이다"), 일반론 시작("최근 .* 업계에서는", "에 대해 알아본다"), 감탄, 질문형 끝, 이모지
- 같은 point 중복(문자 유사도 0.8 이상) 경고
- **도식 판단 경고 두 가지(검수자 입력으로 넘김)**
  - 누락 의심: numbers가 비었는데 근거에 같은 단위 값이 3개 이상 / events가 비었는데 근거에 날짜 다른 사건이 3개 이상
  - 남발 의심: numbers 그룹이 2개 값뿐인데 baseline이 없음 / events 2개인데 flow_is_point 없음

### 렌더 가독성 검사 (checks/diagrams.py, S6에서 화면 연결 후)
- export가 그린 SVG를 Playwright로 열어: 글자가 틀 밖으로 넘치는지, 라벨끼리 겹치는지, 막대에 단위가 있는지, 제목이 있는지 코드로 확인(VisEval의 유효성, 적법성, 가독성 중 코드로 잴 수 있는 것)
- 주 1회 스크린샷을 judge 모델(gemini-3.8-flash, 이미지 입력)에 1~5점으로

### 검수자에 더할 질문 (roles/critic.md)
- 도식마다 "이 도식을 빼면 읽는 사람이 잃는 것이 있나?" 없으면 이슈 `overuse`
- 누락 의심 경고가 있으면 "이 비교나 흐름을 문장으로 읽는 게 그림보다 느린가?" 그렇다면 이슈 `missing_diagram`
- 충실성은 문장을 원자 사실로 쪼개 하나씩 근거와 대조(FActScore 방식). 지지되지 않은 사실마다 `unsupported`

## ③ 관문 B 채점 (eval/)
채점자: judge(gemini-3.8-flash). 입력은 TopicPage + 근거 원문 + plan.angle. 코드 검사를 통과한 것만 채점자로.

통과 기준은 **예/아니오 질문 + 한 줄 비평**이다(문서 35, Hamel Husain). 1~5점은 같은 호출에서 함께 받아 보고용으로만 기록한다.

| 항목 | 대응 표준 | 채점 방식 (judge 질문) | 문턱값 |
|---|---|---|---|
| 근거 충실성 | G-Eval 충실성, FActScore | 채점자가 문장을 원자 사실로 쪼개 각각 지지/비지지 판정 → 코드가 **지지율 = 지지된 사실 / 전체 사실** 계산 | 모든 토픽 100% |

- **judge 맞추기:** 도식 판단 라벨과 같은 토픽 20개에 사람이 항목별 통과/실패 + 한 줄 비평을 단다(한 번에 같이 라벨). judge와 사람의 일치율이 80% 미만인 항목은 사람 비평을 judge 프롬프트 예시로 넣고 다시 잰다(최대 3회). 그래도 미달이면 그 항목은 사람 판정을 기준으로 한다
- 검수자(critic)도 같은 라벨로 일치율을 잰다(반려해야 할 것을 반려했나)
- LLM 채점자는 LLM이 쓴 글을 후하게 보는 경향이 있어, 주 1회 사람이 10건을 확인한다
- ROUGE 같은 단어 겹침 지표는 쓰지 않는다(사람 판단과 상관 낮음)

# S5 역할 메모: 요구사항, 과거 교훈, 측정 (설계 세션 → 코드 세션, 2026-10-09)

> 역할 md 초안(roles/decide, editor_select, writer, writer_revise, critic)과 skills/diagrams.md는 설계 세션이 쓴 **가벼운 초안**이다. 고도화(문구, 함정 예시, 실제 출력으로 예시 교체)는 코드 세션이 채점 결과를 보며 한다(COMMON E1: 가설 1개, 같은 실패 2회면 그 방향 종료).
> 이 파일은 역할 설계의 근거 중 **저장소에 없던 것**(S1~S4 리뷰에서 얻은 교훈과 결정)을 옮긴 것이다. 괄호의 번호는 설계 세션 프로젝트 문서 번호(예: 61 R10 = S2~S3 PR 리뷰의 지적 R10). 저장소에 이미 있는 근거는 agents_spec.md(26), prompt_guide.md(35), writer_draft.md(29), writing_visual_guide.md(32).
> 결정 자체(묶기 문턱값, 라운드, DB 표 등)는 S5_TASK.md가 기준이다. 여기는 "왜"와 "무엇을 조심할지".

## 0. 모든 S5 역할 공통

### 0.1 md와 코드의 나눔
- 모델이 알아야 할 것은 md, 반드시 지켜져야 할 것은 코드(53 Q1). 코드가 값을 정하는 칸 목록은 출력 클래스의 **ClassVar `ENFORCED_FIELDS`** 로 선언(S5 새 역할은 처음부터 ClassVar, 61 R6)
- 코드 규칙은 두 종류로 나눈다(53 Q1)
  - ① 코드가 값을 고정하는 칸 → enforce 후 값으로 통과 판정
  - ② 모델 품질을 드러내는 정리 규칙(근거 밖 수치 삭제, 목록 밖 id 삭제 등) → **원래 출력**으로 문턱값을 재고, 원래 ↔ enforce 후가 다른 비율을 "모델 일치율"로 따로 적음
- 칸은 반드시 `fix()`로만 바꿔 enforced 기록을 남긴다. eval은 원래 출력과 enforce 후 출력을 둘 다 기록(53 2장)
- **품질 검사는 원래 출력을 대상으로.** repo_analyst의 "근거 없는 why_trending이면 attention"은 enforce 후 값을 봐서 늘 통과했다(61 R4)
- 판단 기준이 모델에게만 있으면 결과가 흔들린다 → 가능한 것은 코드 규칙으로 고정(예: 본문 N자 미만이면 attention, 48 지적 2)

### 0.2 모델 성향 (6주차 벤치 47, 45)
- **모든 모델이 작성자 형식 규칙을 놓쳤다**: 명사형 포인트, 형광 개수, 숫자 그대로 쓰기(512K → 512,000). 작성자 묶음 전 항목 통과 모델 없음, qwen3.8-27b 0.72. 모델을 바꿔 풀 문제가 아니므로 코드 검사 + 수정 라운드가 설계 전제(47)
- 검수(F)는 qwen3.8-27b 1.00(로컬 0.96): 심은 오류를 모두 잡고 깨끗한 초안은 통과. 계열 분리는 보류(Gemma 31B F 0.50) → critic은 같은 모델의 새 메시지 목록(47)
- gpt-oss-20b는 없는 오류를 다수 지적 → **깨끗한 초안도 critic 픽스처에 포함**(과잉 지적 측정)(45)
- Gemma 31B가 구조화 출력 + 온도 0에서 JSON 중간부터 공백 반복 → max_tokens 도달. 제공사를 바꿔도 재현 → **출력 잘림 감지 필수**(45)
- 추출 생략 실패(Gemma 26B가 quotes·numbers를 빈 배열로) → 빈 근거 배열 검사(45)
- 스키마 거부 메시지에는 칸 경로 + 짧은 한국어(예: `origin.kind: 허용 값 아님 (허용: …)`). 모델이 객체 대신 문자열을 보내고 같은 호출을 반복한 사례(47, 53 M4)

### 0.3 입력·보안
- 수집 글은 `<data>`/`<document>`로 감싸고 그 안의 지시를 따르지 않게. item_card 인젝션 픽스처에서 확인됨. **S5 역할에도 인젝션 픽스처 유지**(61 부록 B, 55 E3)
- 역할 입력에 이미지를 중첩하지 않는다(최상위 ImageFile만 인식, 57 지적 6). S5 역할은 이미지 입력 없음
- 원문 표기를 보존해야 하는 칸이 있는 역할은 style_ko includes 여부를 따로 판단(57 지적 8). → decide·critic은 includes 없음, writer는 있음(숫자·고유명사는 근거 표기 그대로라는 규칙을 md에 명시)
- 입력이 비면 LLM을 건너뛰고 대체 동작(57 2장 원칙)

### 0.4 실패 시 대체
- decide 실패 → 묶지 않음(same=false)
- editor_select 실패 → 점수 순 상위 N, 1위 리드, briefing_plans.source=fallback
- writer 실패 → 그 토픽 제외 + attention "작성 실패"
- critic 실패 → 코드 검사만 통과한 판으로 + attention "검수 실패"
- writer_revise 실패 → 이전 라운드 판 유지, 남은 이슈 자리는 check=true

## 1. decide (묶기 판단)
**요구사항**: 항목 쌍 하나 → reason → same → confidence. 0.6 미만은 코드가 묶지 않음. 호출 상한 주 60회(S5_TASK 묶기 기준)
**교훈**
- 임베딩만으로는 고객 사례 글과 관심 글을 가르지 못했다(Chatham 0.356, Barclays 0.329, Anthropic $100M 0.330, SynthID Bio 0.366). 유사도 수치만으로 같은 대상을 정하지 말 것 → md에 "고유명사로 판단"(61 R9)
- 짧은 글은 임베딩 점수가 낮게 나옴(Simon Willison 0.293, 0.279). 묶기에서 짧은 글이 손해 → 1개짜리 묶음 비율과 경계 근처 쌍 표로 확인(61 3장)
- 표기 차이 규칙: 공백만 다르면 같음(Frontier Code = FrontierCode). spoken = screen인 표기 쌍은 쌍으로 두지 않음(57 지적 2, 60 R2). 숫자·버전이 다르면 다른 대상(S5 결정)
- 장치 간 임베딩 차이 기준 "판정 바뀐 항목 0 + 최대 차이 0.01 이하"(bf16 실측 0.005). 묶기 문턱값 근처 판정이 장치마다 달라지지 않는지 같은 방식으로(61 N5)
**픽스처(8~10)**: 같은 발표 글↔영상, 같은 제품 글↔레포, 같은 회사 다른 제품, 버전 다름, 같은 분야 다른 회사, 한쪽이 언급만, 음차↔영문, 고객 사례 ↔ 제품 발표, 인젝션 1
**측정**: 라벨 대비 정확도, **오병합(라벨 false인데 same=true & conf≥0.6) 0**

## 2. editor_select (편집장 선별)
**요구사항**: 26 6장. 모든 후보에 decision(reason → action), 토픽 4~10(최대는 목표 아님), 리드 1, 합치기·나누기는 기존 범위 안, slug_hint
**교훈**
- **이유 문장에 입력에 없는 사실이 들어갔다**(editor_plan): 입력은 origin_link_kinds=other(The New Stack)인데 "원본 후보 공식 블로그(OpenAI)", slides 0편인데 "슬라이드 판독 예산을 다른 항목에 배분". judge는 3/3 통과, 2차 채점 1/3(일치율 33.3%) → md에 "입력 값만 인용" + **코드나 judge가 reason 속 값을 입력과 대조**(61 R11, 부록 D)
- 고객 사례 홍보 글은 관심 밖인데 item_card가 Basis·Jump Trading 고객 사례를 relevance high로 줬다 → 선별이 두 번째 거름망. md에 규칙 + 함정 예시(61 R9, N4)
- 관심 기준: AI 시장 경향, 개발 실무·경험(코드, 리뷰, 커밋, 도구 사용, 생산성). 커리어, 글쓰기, 비 AI 도구 소개는 밖. 에너지(태양광, 전력망), 통신, 군사, 인사는 drop(61 3장, 부록 A). 제외어 4개는 S5 첫 커밋에(61 N6)
- **md의 수량 상한은 넘을 수 있다**: editor_plan이 md의 "80%까지만"(72분)을 넘어 84분 계획. 토픽 수 상한, 리드 1은 **코드가 검사·자름**(61 R11)
- 데이터·수치가 많은 자료를 놓친 사례(741% 등 데이터 발표를 whisper만, 400개 기업 데이터 영상을 큐 밖) → 선별 기준에 "수치·데이터가 있는가"(61 부록 E)
- 위치 편향 대응: 후보는 cluster_id 고정 순서(26 0.7)
- **넣을지와 순서를 나눈 이유**(설계 결정 C-13, 사용자 검토): 개발 경험담처럼 원래 글 하나뿐인 주제가 근거 수 때문에 빠지지 않게. 근거·채널 수는 순서에만 쓰고, drop 이유도 "근거 1건"이 아니라 thin(내용이 짧아 페이지가 안 됨). 선별 입력 상위 20 점수도 관련성 우선
**픽스처(8~10)**: 보통 주, 후보 부족 주(4개 미만), 고객 사례 포함, 지난 토픽 중복, 진짜 후속, 섞인 묶음(나누기), 따로 묶인 같은 대상(합치기), 관심 밖(에너지), 인젝션 1
**측정**: 코드 검증 통과(리드 1, 개수, 범위), drop 이유 라벨 일치, reason 속 값의 입력 대조 위반 0

## 3. writer (작성자)
**요구사항**: 29 ① 그대로(writer_draft.md). 코드 규칙 29 ②, 도식 skills/diagrams.md
**교훈 — 가장 흔한 실패는 근거 밖 서술**

  - 방향 반전: "감속 근거가 약해졌다" → "생산성 효과가 기존 보고보다 낮아졌다"(34873)

- 인용 밖 서술 예: 고유명사(CyScenarioBench, METR, "caveman", "플로리다주"), 벤치 이름("GPQA 다이아몬드 기준"), 최상급("기술 역사상 가장 빠른"), 결과 서술("비용이 증가한다", "규제된 금융 환경에서도 확장 가능")(61 부록 B)
- 수치 왜곡: 범위·부등호("최대 50%" → "50% 이상"), 날짜와 모델 버전 섞기, 제목에서 가져온 이름(58)
- **서로 다른 근거 구간을 한 문장에 합침**(5wDz 안전 표준, yNPS BM25+grep), 아직 나오지 않은 내용을 미리 요약해 붙임(영상 타임라인 Q2 실패 대부분) → 각 문장은 그 근거 id 범위 안의 내용만(58)
- 근거가 없으면 사실처럼 쓰지 말 것: repo_analyst가 "github_repo … 403 실패"를 evidence에 사실처럼 씀(61 R1). claude-mem "v13.32.0~ 릴리스 5개 연속"은 evidence 2개에 없음(61 R4)
- 근거 id 개수에 상한을 두고 넘으면 enforce(video_summary MAX_EVIDENCE=3 선례, 56 D2). writer는 point당 refs 상한 3 제안
**코드 검사에 그대로 쓸 수 있는 것**
- `numbers_outside_quotes`(61 R2): 본문 숫자가 근거에 있어야 함(영어 수 단어 one~ten 허용). 21건에 적용 시 오탐 0
- `figures` 추출 규칙(62 R3): %, 배, 소수, 4자리 이상만. 버전·큰 단위·작은 개수 제외("28종" 오탐 없음)
- 제품·모델명 속 숫자(Orbit-7의 7)를 근거 밖 숫자로 세는 오탐 주의(45)
- 수치 비교는 S4 align의 수치 정규화를 공통 모듈로 옮겨 사용(S5 결정 C-4·C-5)
**픽스처**: 비율 지표라 20(토픽 20개, E3 예외). 보통 / 빈칸 / 함정(값 2개, 인용 밖 내용) / 인젝션 포함
**측정**: 29 ③ 그대로(충실성 100%, 나머지 90%, 도식 남발 0·누락 20개 중 1 이하)

## 4. writer_revise (작성자 수정)
**요구사항**: 지적된 칸만, 근거로 못 고치면 삭제. **고친 칸만 출력**(changed[] + 새 값)하고 코드가 이전 판에 합침(페이지 전체 재출력은 시간이 들고 지적 안 된 문장이 바뀔 위험). 지적 안 된 위치를 냈으면 코드가 되돌림(29, 26 0.7, 설계 결정)
**교훈**
- 형식 위반(명사형, 형광, 숫자 표기)은 원래 이 단계에서 고치는 것이 설계 전제였으나, S5 결정 C-5로 **고칠 수 있는 형식은 코드가 직접 고치고 반려하지 않음**. revise에 오는 것은 의미 이슈만(47, C-5)
- "지적된 칸만"은 md만으로 지켜지지 않는다 → 코드 비교로 검증, 되돌린 횟수를 기록(53 Q1, 47)
- revise가 바꾼 것도 fix 계열처럼 기록(changed + 코드 diff)해야 채점에서 원래와 수정을 함께 볼 수 있음(53 M2)
- 같은 이슈가 같은 자리에 두 번 남으면 더 돌리지 않고 check=true(C-5, 55 E1과 같은 원리)
**픽스처(8~10)**: 이슈 유형별 1개씩 + 지적 안 된 칸을 고치고 싶어지는 함정 + 근거 원문 없음
**측정**: 지적 안 된 칸 변경률(되돌림 전 원래 출력 기준), 이슈 해결률(다음 라운드 critic 기준)

## 5. critic (검수자)
**요구사항**: 26 8장 + 29 "검수자에 더할 질문". atoms → fact_support → issues → status. 판정 기준은 **근거 원문**(요약 칸 아님)
**교훈 — judge·검수가 너그러웠던 세 유형**
- 불일치는 모두 "judge pass, 2차 채점 fail" 한 방향(61 3장). 놓친 유형:
  1. 인용 밖 서술(item_card judge Q1 21/21 pass ↔ 2차 10/21, 완화 18/21)
  2. 입력에 없는 reason(editor_plan judge 3/3 ↔ 2차 1/3)
  3. 부분 확인(text_analyst judge 16/16 ↔ 2차 12/16)
- 영상 요약 judge는 24개 Q 전부 pass, 불일치 6개는 모두 judge가 놓친 fail(근거 창 밖 내용, 30초 밖 라벨)(58)
- 도구가 전부 실패한 무효 실행인데 코드 10/10, judge 10/10(61 R1) → 근거가 없으면 통과로 두지 말 것(critic md "막혔을 때")
- **부분 확인은 unsupported**: 수치가 여럿 든 문장을 confirmed로 했는데 일부 수치가 인용에 없음(it201 1300개·1%·99%, it933 8.9%·2.62배, it997 51.3%). 같은 수치 단독이면 not_found였는데 묶이면 confirmed가 됨 → 원자 사실 단위 대조로 막음(61 R3, 부록 F)
- 모순 ↔ 없음 구분: "28종"은 인용과 모순이 아니라 없을 뿐(not_found). differs(다름)는 수치가 인용에 없는 것이 정상(62 지적 1). → critic 비평에 둘을 구분, type도 다르게(모순 = number_mismatch/overclaim, 없음 = unsupported)
- 이슈 유형 근거 사례: number_mismatch(단위 누락, 부등호), overclaim("기술 역사상 가장 빠른", "확장 가능"), wrong_ref(근거 창 밖, 다른 구간 합치기)(61 부록 B, 58)
- 문체·형광은 코드 몫이라 반려 사유 아님(26 0.7, C-5)
**픽스처**: 비율 지표라 20(writer 라벨과 같은 토픽). 심은 오류 유형별 + **깨끗한 초안 다수**(과잉 지적 측정) + 매끄럽지만 근거 밖 내용 + 근거 원문 없음
**측정**: 라벨 대비 반려 정확도(반려해야 할 것을 반려, 깨끗한 것을 통과), 반려 후 통과율, 출력 잘림 0

## 4. 배경, 목표, 원칙
- 배경: 개발자로 일하며 필요했던 것은 일정 관리와 신규 기술 트래킹. 기술 트래킹을 선택. 영상 분석, GitHub 트렌딩, 글 브리핑 오픈소스는 기능별로 있지만 합치고 동적으로 관리하는 것은 없음
- 목표
  - **실제로 계속 쓰는 개인 기술 트래킹 도구** (최우선)
  - 글, 영상, GitHub 소스의 통합 수집과 교차 연계
  - 관심과 소스 변화에 맞춘 동적 관리
  - 로컬 AI 기반 상시 운영
- 진행 원칙: 핵심 요구사항을 먼저 고정하고, 그 범위 안에서 단계적으로 확장. 크게 벌리지 않는다
- 품질 원칙: 리포트의 모든 문장에 출처, 검수자가 근거와 대조(지어낸 내용 0건)
- 수집 기간(2026-10-07 결정): GeekNews RSS는 최근 50건 약 24시간, AI타임스는 50건 약 1.5일만 담는다. 그래도 매일 수집을 미리 시작하지 않고, **필요할 때 지난 기간을 한 번에 긁어오는 백필**로 해결한다(과거 글은 목록 페이지와 아카이브에 남아 있음). RSS만으로 부족한 소스는 목록 페이지 파서를 둔다. GitHub Trending 페이지는 과거 기록이 없으므로 그 주에 실행해야 함

## 6. MVP (8주차)
- 한 줄기: 소스 6개로 한 주치 브리핑이 사람 손 없이 나오고, 슬라이드에만 있던 수치가 출처와 함께 들어간다
- 포함: 글 6 + 유튜브 1(영상 2~3편) + GitHub(주간 트렌딩 + 추적 레포 4개) / 원본 추적(글 분석가) / 영상 슬라이드 판독 / 표기 정규화 v0 / 토픽 묶기 / 인용 브리핑 + 검수 반려 루프 / 실행 로그
- 발행: **자동 발행 + 사후 감시(human-on-the-loop).** 승인 단계는 초반 품질 조정 기간에만 켜는 설정(approval_mode)이고 화면에는 없음. 검수를 통과하지 못한 문장은 '확인 필요'로 표시된 채 발행
- 사람이 개입하는 곳(이후): 키워드 확정, 별칭 후보 승인, 소스 추가/끄기. MVP에서는 설정 파일로 고정
- MVP 고정 소스(확정분): 글 GeekNews(`news.hada.io/rss/news`), OpenAI News(`openai.com/news/rss.xml`, 설명만 → 본문 추출), Anthropic News(공식 RSS 없음 → 커뮤니티 생성 피드 또는 목록 페이지 직접 파싱) / 유튜브 Tech Bridge(@TechBridge-KR, channel_id `UC895rbZX2iXLTDfji7W4PfA`, 해외 기술 발표에 한국어 자막). 추가 글 소스(확정): Google DeepMind 블로그(`deepmind.google/blog/rss.xml`), Simon Willison's Weblog(`simonwillison.net/atom/everything/`, 전문 + 원본 링크 많음 → 원본 추적 시연), AI타임스(`aitimes.com/rss/allArticle.xml`, 국내 뉴스, 하루 20~25건). 글 6 + 영상 1 + GitHub. Hugging Face 블로그는 이후 후보. 추적 레포 4개: ollama/ollama, NousResearch/hermes-agent, openai/codex, anthropics/claude-code. 키워드 10개 + 제외어. 설정 원본은 프로젝트 문서 27(`config/sources.yaml`, `config/keywords.yaml`)
- **MVP 범위(2026-10-07 확정): 소스와 키워드는 설정 파일에 미리 정해 둔다(하드코딩).** 화면에서 바꾸는 기능은 MVP 밖. MVP는 정해진 소스, 키워드로 분석과 브리핑이 나오는 것까지
- 제외: 관심사 → 키워드 자동, URL 자동 판별, Threads, 아카이브 Q&A, 메신저 알림, 예산 관리, 소스 자동 추천

## 7. 성공 기준 (1주차 문제정의서)
- 동향 파악 시간 주 3시간 → 15분
- 발화에는 없고 슬라이드에만 있는 핵심 정보 80% 이상 포착(영상 10편 수동 라벨)
- 표기 정규화 정확도 90% 이상, 서로 다른 대상 오병합 0건
- 모든 항목에 출처(링크 또는 영상 타임스탬프), 지어낸 내용 0건
- 소스, 키워드 변경은 코드 수정 없이 화면에서 3분 이내 반영

## 8. 아키텍처
- **코어 하나 + 로컬 모델.** Dify는 쓰지 않는다(교수님 확인, 필수 아님). 역할 로직은 파이썬 코어 한 곳에만. Hermes, Paperclip은 나중에 API/MCP로만 들어온다

| 이름 | 하는 일 | 주소 | 공개 |
|---|---|---|---|
| trendsit-web | 화면 (지금은 정적 예시 사이트) | 127.0.0.1:8788 | trendsit.jiseop.com |
| trendsit-api | FastAPI + MCP (이후) | 127.0.0.1:8789 | 없음 |
| trendsit-nightly | 매일 02:00 얕게 훑기 → 편집장 계획 → 깊게(글, 영상, 레포 분석가) → 묶기 | 단발 | - |
| trendsit-weekly | 월 07:00 선별, 작성, 검수 → 발행 | 단발 | - |
| Ollama | 유일한 추론 서버 | 127.0.0.1:11434 | 없음 |

- 스케줄러는 launchd 하나. 무거운 작업은 단발 프로세스에서만, 웹은 조회만(Cloudflare 100초 제한)
- 저장: SQLite 하나(칠판) + sqlite-vec(벡터) + FTS5(trigram). 역할끼리 직접 대화하지 않고 산출물을 칠판에 쓰고 읽는다
- 화면(2026-10-07 결정): **브리핑은 정적, 관리 화면은 이후 FastAPI**
  - 브리핑(홈, 토픽): 발행할 때 예시 JSON과 같은 형식의 주차별 스냅샷(`data/published/<주차>.json`)을 만들고 build.py로 정적 HTML 생성. 공개, 쓰기 없음. 이후 Cloudflare Pages로 옮기는 선택지(데모데이 백업)
  - 관리 화면(소스, 키워드, 실행 기록): MVP는 배치가 끝날 때 정적으로 생성, 변경은 설정 파일이나 CLI. MVP 이후 FastAPI가 SQLite를 직접 조회해 그리고 쓰기 버튼 추가(Access 먼저). 템플릿과 CSS는 build.py와 같은 것을 씀
  - SQLite 직접 읽기로 충분: WAL + busy_timeout, 배치는 짧게 커밋, 조회 API는 읽기 전용 연결, DB 접근 코드는 한 곳, 무거운 작업은 작업 큐 테이블

## 9. 에이전트 역할과 흐름 (상세: 프로젝트 문서 26)
- 패턴: 오케스트레이터-워커 + 작성-검수. 판단이 필요한 곳만 LLM, 나머지는 코드. 역할 수 5개 제한은 엄격하게 보지 않음
- 형태 구분: **다음 행동을 누가 정하느냐.** 도구 결과를 보고 모델이 다음 행동을 고르면 에이전트, LLM이 판단만 내고 코드가 정해진 분기를 실행하면 "판단 + 코드 분기", 입력이 정해진 출력 하나면 "LLM 1회"

| 역할 | 형태 | 시점 | 출력 |
|---|---|---|---|
| 편집장 · 계획 | 판단 + 코드 분기 | 02:00 | CollectionPlan (항목별 깊게 볼지, 최대 깊이, 이유) |
| 글 1차 요약 | LLM 1회 | 02:00 | ItemCard v1 (+ 원본 확인 필요 판정) |
| 글 분석가 | 에이전트 | 02:00 | ItemCard v2 (원본, 추적 경로, 요약 글과 원본 대조) |
| 영상 분석가 | 판단 + 코드 분기 | 02:00 | VideoDigest (슬라이드 전용 수치, 타임라인) |
| 레포 분석가 | 에이전트 | 02:00 | RepoCard (하는 일 한 문장, 신호, 과열 신호) |
| 묶기 | 코드 + 판단 함수 | 02:00 | TopicCluster 후보 (애매한 쌍만 decide()) |
| 편집장 · 선별 | LLM 1회 | 07:00 | BriefingPlan (순위, 리드, 합치기, 나누기, 버리기) |
| 작성자 | LLM 1회 | 07:00 | TopicPage (근거 id, 수치와 사건은 구조화) |
| 검수자 | 코드 검사 → LLM 1회, 새 컨텍스트 | 07:00 | ReviewVerdict (반려 최대 2회) |
| 설정 도우미 | 대화형 에이전트 | 10주차 | 소스, 키워드 후보 |

- **02:00 흐름: 얕게 훑기 → 계획 → 깊게 → 묶기**
  1. 얕게 훑기(깊이 1, 모든 항목): 글은 원글 본문 → 필터 → 1차 요약, 영상은 메타데이터와 자막 유무, 레포는 트렌딩 수치 + README
  2. 편집장 계획: 세 채널의 깊게 볼 후보를 함께 보고 항목별로 깊게 볼지와 최대 깊이를 정함(같은 맥, 같은 모델, 같은 밤 시간을 나눠 쓰므로)
  3. 깊게(고른 항목만): 글 분석가, 영상 분석가, 레포 분석가
  4. 묶기 + 과거 대조
- **깊이 규칙**
  - 깊이 = 따라간 단계 수. 글: 1 원글 / 2 원글이 링크한 원본 / 3 그 원본이 링크한 원본 / 4 예외. 영상: 1 메타데이터 / 2 자막 또는 전사 / 3 슬라이드 판독. 레포: 1 수치 + README / 2 커밋, 기여자, 릴리스 / 3 연결된 논문, 문서
  - 편집장이 항목별 최대 깊이를 주고 에이전트는 그 안에서 일찍 멈출 수 있음. 전체 상한 4는 코드가 강제(가져온 페이지마다 출발 페이지를 기록해 경로 길이로 셈)
  - 상한 세 겹: 깊이 / 항목당 도구 호출 수(예: 6) / 밤 전체 예산
  - 깊게 보다 찾은 새 후보는 그날 넓히지 않고 다음 날 후보로만 남김
  - 처음 1~2주는 기본 2, 최대 3. 원본을 찾은 깊이 분포를 보고 4를 열지 결정
- 07:00 흐름: 선별 → 토픽마다 작성 → 코드 검사 → 검수(반려 최대 2회, 남은 이슈는 확인 필요) → 발행 → 지식 누적
- **역할 구현 방식**
  - 에이전트 정의 = md 하나(`roles/<이름>.md`): 앞부분에 실행 설정(모델, 출력 스키마 이름, 허용 도구 목록, 최대 깊이와 걸음, task, core_rules), 본문은 **공통 템플릿(문서 35)**: 목표(+왜) / 입력 / 판단 기준 / 출력 / 막혔을 때 / 예시 3개(보통, 빈칸이 맞는 경우, 함정)
  - **프롬프트 작성 규칙(문서 35, COMMON 6.1):** LLM 역할 11개를 형태 다섯(추출, 판단, 도구 에이전트, 생성, 판정)으로 나눠 같은 형태는 같은 뼈대. 메시지는 system = 역할 md(정적) / user = `<data>`(문서별 `<document id source>` 태그) → 과제 → 핵심 규칙 3줄. 지시에 이유를 붙이고 강조는 하나만. **출력 스키마는 인용·이유 칸 먼저, 결론 칸 나중**(추론을 끈 모델 대응). 도구 에이전트는 "추측 대신 도구로 확인", 멈추는 조건 3개, "못 찾음은 정상". 고칠 때는 실패 분류 → 한 번에 하나(md 문구 → 예시 → 칸 순서 → 코드 → 모델) → 같은 픽스처로 비교
  - **채점(judge, 검수자):** 통과 기준은 예/아니오 질문 + 한 줄 비평, 1~5점은 보고용. 역할마다 사람 라벨(통과/실패 + 비평) 20건으로 judge 일치율을 먼저 재고 80% 미만이면 사람 비평을 예시로 넣어 다시 잼. 같은 계열 모델끼리 채점 금지
  - 여러 역할이 같이 쓰는 절차와 규칙은 지침 md로 따로 둠(예: 원본 추적, 문체)
  - 도구, 출력 스키마, 입력 조립, 상한과 보안은 파이썬 코드. 원칙: **모델이 알아야 하는 것은 md, 반드시 지켜져야 하는 것은 코드**
  - 에이전트 루프는 직접 얇게 구현(2026-10-07 결정): 공식 `openai` 파이썬 SDK(HTTP, 재시도) + pydantic(검증) 위에 루프와 실행 기록만 직접 작성(약 200줄). 프레임워크(PydanticAI, OpenAI Agents SDK, LangGraph, CrewAI)는 쓰지 않음. 반복 코드가 부담되면 run_agent 안쪽만 PydanticAI로 교체 가능하게 바깥(md 정의, 도구 함수, 실행 기록)을 분리
  - `run_role()`(1회 호출), `run_agent()`(도구 루프)가 OpenAI 호환 /v1 호출(개발은 OpenRouter, 이후 Ollama). 실행 로그에 역할, 프롬프트 버전(파일 해시), 모델, 입출력, 지연 기록
  - 모든 출력에 `log`(한 줄, 명사형)와 `attention`(사람이 봐야 하면 true) → 실행 기록 화면
- 도식은 작성자의 구조화 출력(수치, 사건, 영상 시각)을 보고 코드 규칙이 고른다. LLM이 그림을 그리지 않는다
- 작성자 지침 v2(문서 29, 근거 문서 32): 형식은 정보의 모양이 정하고 기본은 문장. 수치 막대는 같은 단위 값 3개 이상 또는 전후 비교(차이가 summary에 나옴)일 때만, 사건 흐름은 3개 이상(2개는 흐름이 쟁점일 때). 도식 종류는 A~D 닫힌 목록. summary 첫 문장 = 결론. 모델 지침은 긍정형, 금지어는 코드 정규식. 평가는 충실성 = 원자 사실 지지율 100%, 표현 선택 = 사람 라벨 20개 대비 누락률·남발률

## 10. 처리 방식 핵심

- 영상(2026-10-07 변경): 맥에 있는 `youtube-analyze` 스킬의 검증된 방식(로컬 mlx-whisper 전사 + ffmpeg 프레임 추출과 중복 제거, 화면 지시 표현 시점 프레임, 프레임별 발화, 전사 품질 판정)을 **참고해 TrendsIT 안에서 직접 구현**한다. 스킬 경로, venv, CLI에 의존하지 않는다. 판단(처리 깊이, VLM 프레임 판독, 발화 대조, 표기 쌍)은 TrendsIT 역할. 전사는 로컬 Whisper 기본, 수동 자막은 보조, 자동 자막은 안 씀. 깊이 2 = `--frames off`, 깊이 3 = `--frames auto/full`, 프레임 상한 20장. 전사 품질이 의심되면 프레임만 근거로. 상세는 reference/youtube_analyze.md

## 11. 화면 (MVP 프론트 기획 v2.1 + 디자인 최종안 v2)

- 키워드: 별칭 후보 승인을 맨 위에, 아래는 키워드에서 별칭으로 뻗는 가지(확정, 후보, 거절)
- 실행 기록 3단: 메뉴는 메인(이번 주차: 봐야 할 판단, 단계 레일, 실행 목록)으로 열림 / 상위는 주차별 목록 / 하위는 실행 1건의 시각별 판단 기록(반려는 초안, 근거, 수정 비교)
- 문체: 요약, 개요는 "~다", 포인트와 화면 문구는 명사형. 해요체 쓰지 않음(작성자 역할 지시문에도 같은 규칙)
- 디자인 규칙은 `docs/02_DESIGN.md`. 요점: 무채색 + 형광 밑줄 하나만 유채색(브리핑은 핵심 내용, 관리 화면은 사람이 봐야 할 것), IBM Plex Sans KR, 카드 그리드 없음

## 13. 모델 계획
- **구현 단계 모델(2026-10-07 변경): OpenRouter `qwen/qwen3.8-27b`.** 2026-08 공개, Apache 2.0 오픈웨이트, 텍스트·이미지·영상 입력, 도구 호출, 구조화 출력, 262K 컨텍스트. 제공사는 DeepInfra BF16 고정(약 $0.15 / $1.875 per 1M), `provider.order`, `allow_fallbacks: false`, `require_parameters: true`. 추론(reasoning) 모드는 기본 끔(필요한 역할만 켬). 모델과 주소는 설정 파일에만
- 품질 비교용: `mistralai/mistral-large-4-0`(2026-10-06 공개, 이미지·도구·구조화 출력, 512K, 할인가 $0.68 / $2.09, 정가 $1.36 / $4.18, 제공사 Mistral 하나). 작성자, 검수자처럼 품질이 중요한 곳의 같은 입력 비교에만
- 방식: 상위 모델로 최소 구현과 완성도 확인 → 에이전트별 LLM 요구, 평가 기준 정리 → 로컬 모델 선정(9주차 로컬 서빙 수업과 맞춤). 실행 기록(입력, 출력, 도구 호출, 프롬프트 버전, 토큰, 지연)은 처음부터 남겨 평가 세트와 기준 답안으로 씀. 스펙마다 같은 입력을 작은 모델로 한 번 돌려 깨지는 곳 확인
- 로컬 후보 비교군: qwen3.5-9b, qwen3.6-35b-a3b, gemma-4-26b-a4b-it
- 임베딩(2026-10-07): **Qwen3-Embedding-0.6B**(Apache 2.0, 약 119개 언어, 한국어 등 아시아 언어 강함, 1024차원, 과제별 지시문 지원). API가 아니라 코드 안에서 직접 실행(sentence-transformers, 클라우드는 CPU, 맥은 MPS) → 비용 0, 개발과 운영이 같은 모델이라 벡터를 다시 만들 필요 없음. 대안 bge-m3(MIT, 가장 많이 쓰임). 로컬 운영 때 Ollama로 옮겨도 같은 모델
- 평가 채점자(2026-10-07): **Google `gemini-3.8-flash`** 하나로 통일. 생성(Qwen), 구현(Claude 코딩 에이전트)과 다른 계열, 텍스트·이미지·영상 입력, 구조화 출력, 추론 모드 지원. Google AI Studio standard 고정($0.75 / $3.75 per 1M, 급하지 않은 일괄 채점은 flex $0.375 / $1.875). 채점 때는 추론 모드 켬. 텍스트 결과 채점, 슬라이드 판독 채점, 상한선 측정 모두 이 모델. 대안: gemini-3.1-pro-preview($2 / $12)
- **API 예산(2026-10-07 재수정): 최소 구현 단계 전체를 20달러 이내로 제한** (키 공통 한도는 50달러, 남은 수업용으로 아낌. 처음 2달러로 적었다가 한도 확인 후 20달러로 고침). 배분 상한: 생성(Qwen) 11 / 채점(Gemini) 4 / 비교, 상한선 측정 2 / 예비 3
  - OpenRouter 키에는 공통 한도 50달러가 이미 있어 바꾸지 않음. 20달러는 코드가 지킴: 요청마다 `usage: {include: true}`로 응답의 `usage.cost`를 기록, 단계 시작 때 `GET /api/v1/key`의 `usage`를 기준값으로 저장해 단계 사용액 = 현재 usage − 기준값. 스펙별 예산(handoff에 명시)이나 단계 상한을 넘으면 코드가 멈춤
  - 응답 캐시(같은 모델, 메시지, 설정이면 재사용). 개발은 1일치 5건 샘플, 한 주치 전체 실행은 최소 구현 끝에 1~2회만
  - 생성은 추론 모드 끔 + 역할별 max_tokens 상한. 채점은 flex, 추론 토큰 상한, 스펙당 픽스처 10개. Mistral 비교는 작성자 토픽 2개만. 배관 확인(S0)은 무료 모델(:free)
  - 대략 추산: 한 주치 전체 실행 약 0.6달러, 채점 1회 약 0.05달러. S2 첫 실행 후 실측으로 고침
- 영상은 원본 영상을 모델에 넣지 않고 프레임 이미지 + 전사 텍스트로 넣으므로, 필요한 것은 이미지 입력
- 에이전트별 작업이 정해지면 역할별 최종 모델을 결정(로컬 전환 포함)
- MVP는 모든 역할에 한 모델. 32GB 맥에서 GPU 기본 한도 약 21GB
- 후보: qwen3.5:9b, gemma4:12b, qwen3-vl:8b / 임베딩 Qwen3-Embedding-0.6B(대안 bge-m3) / 전사 mlx-whisper large-v3-turbo
- 선별: OpenRouter로 정확도 먼저 비교 → 상위 2~3개만 로컬 측정. Jev는 관련성, 처리 깊이 같은 판단의 비교군
- 고도화: Ornith(도구 호출, 계획) + 한국어 강한 모델. 작성자와 검수자는 다른 계열 모델

## 14. 홈서버 규칙
- 맥: M1 Max 32GB, 집, 상시 켜짐, 자동 로그인
- 공개 경로: 브라우저 → Cloudflare(DNS + Access) → 터널 `home` → 맥 cloudflared → 127.0.0.1:포트
- 터널 규칙 `~/.cloudflared/config.yml`, 새 규칙은 마지막 404 규칙 위에
- 기존 앱 pt.jiseop.com(8787, Access 잠금)은 건드리지 않는다
- 피할 포트: 80, 8443, 5003, 5000, 7000, 8081, 8787, 11434. TrendsIT는 8788(web), 8789(api)
- 앱은 127.0.0.1 바인딩만. 잠글 앱은 Access 먼저, 그다음 터널/DNS. 정적 예시 사이트는 공개(쓰기 기능, 비밀 없음). **실제 앱으로 바꾸기 전에 Access를 먼저 만든다**
- launchd 이름 `com.jiseop.<앱>`, 로그 `~/Library/Logs/<앱>.log`
- 비밀(`~/.cloudflared/cert.pem`, 터널 json, `api-token`, 이후 `~/.config/trendsit/.env`)은 출력, 복사, 커밋 금지
